# PHASE_6_FINANCE.md — Фаза 6: Финансы и отсрочки

> Ветка: `feature/light-ui`. Только фронтенд, данные в памяти (`store.js`).
> Основа проверена по коду: у заказа уже есть `paid`, `paymentDue`,
> `clientPrice`, `costPrice`; есть `saveOrder`, `addHistory`; в FSM есть
> паттерн guard `requiresAccepted`. Фаза 6 достраивает поверх этого
> финансовый контур и блокировку отгрузки без оплаты/отсрочки.

---

## 0. Цель фазы

Дать компании три вещи:

1. **Раздел «Финансы»** — сводка по деньгам: выручка, себестоимость,
   прибыль, дебиторка (долги), оплаты. Разрез по периодам и клиентам.
2. **Отсрочка платежа** — заказ можно отгрузить в долг, если оформлена
   согласованная отсрочка (кто согласовал, до какой даты, на какую сумму).
3. **Гейт отгрузки** — нельзя перевести заказ в отгрузку/завершение, пока
   он не оплачен ИЛИ по нему нет действующей согласованной отсрочки.
   Это бизнес-блокировка №2 из ТЗ §13 (`MASTER_PLAN.md` §7).

Принцип из `CLAUDE.md`: данные управляют поведением, деньги — целые числа
(копейки/рубли, не float), guard'ы — чистые функции без DOM.

## 2. Модель данных (расширение store.js)

### 2.1. Заказ — новые поля

Добавляем к заказу (значения по умолчанию — в фабрику создания заказа и в
демо-данные):

```
// финансовый блок заказа
clientPrice   : int | null     // сумма к оплате (уже есть) — это "выручка заказа"
paidAmount    : int            // сколько фактически оплачено (0 по умолчанию)
paid          : bool           // true, когда paidAmount >= clientPrice (уже есть, делаем производным)
payments      : []             // массив платежей по заказу (см. 2.2)
deferral      : null | {…}      // объект согласованной отсрочки (см. 2.3)
paymentDue    : ""             // срок оплаты (уже есть)
```

> `paid` перестаём выставлять руками — он становится следствием:
> `paid === (clientPrice != null && paidAmount >= clientPrice)`.
> Пересчитываем в одной функции `recalcPaid(order)` при каждом платеже.

### 2.2. Платёж — элемент массива `order.payments`

```
{
  id       : "PMT-0001",   // сквозной номер
  amount   : int,          // сумма платежа, руб
  date     : "2026-07-20", // дата поступления
  method   : "нал"|"безнал"|"карта",
  who      : staffId,      // кто провёл (бухгалтер/менеджер)
  note     : ""            // комментарий (номер счёта, УПД и т.п.)
}
```

Частичные оплаты допускаются: сумма платежей может копиться до `clientPrice`.
`paidAmount = sum(payments.amount)`.

### 2.3. Отсрочка — объект `order.deferral`

```
{
  approvedBy : staffId,     // КТО согласовал (director/accountant)
  until      : "2026-08-10",// до какой даты разрешён долг
  amount     : int,         // на какую сумму разрешена отсрочка (обычно = clientPrice)
  reason     : "",          // основание (постоянный клиент, договор №…)
  createdAt  : "2026-07-20"
}
```

Отсрочка = «разрешение отгрузить в долг». Действующая, если
`until >= сегодня`. Просроченная отсрочка (`until < сегодня` и заказ не
оплачен) → красный флаг в «Финансах» и в карточке заказа.

### 2.4. store.js — новые репозитории

Добавить к возвращаемому объекту стора (рядом с `saveOrder`):

```
addPayment(orderId, payment)      // пушит платёж, пересчитывает paidAmount/paid, пишет в history
removePayment(orderId, paymentId) // откат ошибочного платежа (роль accountant/director)
setDeferral(orderId, deferral)    // ставит/меняет отсрочку, пишет в history
clearDeferral(orderId)            // снимает отсрочку
getFinanceSummary(period)         // агрегат: выручка, себестоимость, прибыль, оплачено, долг
getReceivables()                  // список заказов с долгом (clientPrice - paidAmount > 0)
```

`getFinanceSummary(period)` возвращает по завершённым/отгруженным заказам за
период:

```
{
  revenue    : sum(clientPrice),           // выручка
  cost       : sum(costPrice),             // себестоимость
  profit     : revenue - cost,             // прибыль
  paid       : sum(paidAmount),            // поступило денег
  debt       : revenue - paid,             // дебиторка (долг)
  ordersCount: N
}
```

Все суммы — целые. Форматирование (`₽ 62 000`) — только в слое отображения.

## 3. Раздел «Финансы» (экран)

Видимость по ролям (из `ROLE_PERMISSION_MATRIX.md`):
`director`, `accountant`, `economist` — видят раздел.
`manager` — **себестоимость и прибыль НЕ видит** (ТЗ §10.6), но видит
оплату/долг по своим заказам. `assistant` — без финансов.

### 3.1. Верх — карточки-сводка (metric cards)

Четыре карточки за выбранный период (месяц по умолчанию):

- **Выручка** — `revenue`
- **Себестоимость** — `cost` (скрыта для manager)
- **Прибыль** — `profit` (скрыта для manager), + маржа в % справа
- **Долг (дебиторка)** — `debt`, красным если > 0

Переключатель периода: «Месяц / Квартал / Год / Всё время».

### 3.2. Середина — таблица оплат по заказам

Колонки: № заказа · клиент · сумма (`clientPrice`) · оплачено
(`paidAmount`) · остаток · статус оплаты · срок (`paymentDue`).

Статус оплаты — бейдж по правилу:

| Условие | Бейдж | Цвет |
|:--|:--|:--|
| `paid === true` | Оплачен | green |
| частично (`0 < paidAmount < clientPrice`) | Частично | cyan |
| не оплачен, есть действующая отсрочка | Отсрочка до ДД.ММ | yellow |
| не оплачен, `paymentDue` прошёл | Просрочен | red |
| не оплачен, срок не наступил | Ожидает оплату | gray |

Строки с «Просрочен» и «Отсрочка просрочена» подсвечиваются (как overdue
в CRM).

### 3.3. Низ — блок «Долги» (дебиторка)

`getReceivables()` — только заказы с остатком > 0, отсортированы по сроку.
Для директора — итоговая сумма долга и разбивка по клиентам (кто сколько
должен). Это прямой ответ на приоритет отчётов заказчика (долги — в списке
приоритетов дашборда).

### 3.4. Действия на экране (модалки, не prompt/confirm)

- **«Внести оплату»** (accountant/director/manager по своим): сумма, дата,
  способ, комментарий → `addPayment`. Поддержать частичную оплату.
- **«Оформить отсрочку»** (director/accountant): до какой даты, сумма,
  основание → `setDeferral`.
- **«Снять отсрочку»** → `clearDeferral`.
- **«Откатить платёж»** (director/accountant) → `removePayment`.

Каждое действие пишет строку в `history` заказа (единый журнал, требование
ТЗ §13 п.5 — нельзя скрыть смену цены/оплаты).

## 4. Гейт отгрузки (главная блокировка фазы)

### 4.1. Где встраивается

В текущей FSM отгрузка/завершение — это переход **`ready → done`**
(менеджер: «Завершить»). Именно на него вешаем финансовый guard, по образцу
`requiresAccepted`.

> Если заказчик считает «отгрузкой» момент `production → ready` — guard
> вешаем туда. По умолчанию берём `ready → done` как «выдача клиенту и
> закрытие». Уточнить одним вопросом при внедрении.

### 4.2. Guard — чистая функция

```
// true → отгрузка разрешена
function canShip(order, today) {
  if (order.paid) return true;                    // оплачен полностью
  const d = order.deferral;
  if (d && d.until >= today) return true;         // есть действующая отсрочка
  return false;                                    // иначе нельзя
}
```

Функция без DOM, без обращения к стору — на вход заказ и дата. Легко
переедет на бэкенд и легко тестируется.

### 4.3. Поведение в UI

- Кнопка «Завершить/Отгрузить» на заказе:
  - если `canShip` → активна, работает как сейчас;
  - если нет → активна визуально, но по клику показывает модалку-объяснение
    «Нельзя отгрузить: заказ не оплачен и нет действующей отсрочки» с двумя
    путями: **«Внести оплату»** или **«Оформить отсрочку»** (для ролей,
    которым это доступно). Менеджеру без прав — текст «обратитесь к
    бухгалтеру/директору».
- Не блокируем кнопку насмерть (по `CLAUDE.md` — объясняем причину, даём
  выход), а не молча гасим.

### 4.4. Побочные записи

При успешной отгрузке через guard — запись в `history`:
«Отгружен (оплачен)» либо «Отгружен по отсрочке до ДД.ММ, согласовал —
{ФИО}». Так журнал показывает, на каком основании ушёл долг.

## 6. Критерии готовности (проверка фазы)

- Раздел «Финансы» открывается у director/accountant/economist; у manager —
  без себестоимости и прибыли; у assistant раздела нет.
- Сводка считает выручку/себестоимость/прибыль/долг корректно за период
  (сверить руками на демо-данных).
- Частичная оплата копится, `paid` становится true только когда набрана
  полная сумма.
- Нельзя завершить/отгрузить неоплаченный заказ без действующей отсрочки —
  выходит модалка с причиной и вариантами.
- Оплаченный ИЛИ с действующей отсрочкой заказ отгружается; в истории видна
  причина (оплата / отсрочка + кто согласовал).
- Просроченная отсрочка и просроченная оплата подсвечены.
- Все денежные значения — целые, форматируются только на экране; в консоли
  ошибок нет.
- localStorage не используется; guard'ы — чистые функции.

## 7. Открытые вопросы к заказчику (не блокируют старт)

1. «Отгрузка» = переход `ready → done` или `production → ready`?
2. Кто имеет право оформлять отсрочку — только директор, или и бухгалтер?
3. Нужны ли частичные оплаты (аванс + доплата) или всегда полная сумма?
4. Отсрочка задаётся датой «до» или числом дней от отгрузки?
5. Нужен ли учёт способа оплаты (нал/безнал/карта) в сводке, или только суммы?
