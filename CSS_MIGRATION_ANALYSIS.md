# CSS_MIGRATION_ANALYSIS.md — Слияние стилей ART-LINE OS

> ✅ **Проверено по коду** (2026-07-15): `style.css` (корень, 199 классов) vs
> `ART-LINE_OS_v1.6/client_reference/styles.css` (433 класса).
> Стратегия слияния — под план `MASTER_PLAN.md` (база — светлый `client_reference`).

---

## 1. Факт: реальные конфликты

### Общие классы (10 значимых)
`.active`, `.badge`, `.done`, `.eyebrow`, `.field-label`, `.hidden`, `.muted`,
`.overdue`, `.sidebar`, `.topbar`.
Самый опасный — `.active` (используется и в табах, и в статусах, и в навигации).

### Общие CSS-переменные (7) — почти наверняка разные значения
`--accent`, `--bg`, `--cyan`, `--green`, `--red`, `--shadow`, `--yellow`.

### Секции SPA
`.section`/`.active-section` — в корне 5 упоминаний, в примере 17. К этим классам
привязана навигация (`applyRole`, `navTo`) — трогать разметку осторожно.

---

## 2. PWA-файлы — важное расхождение

- **Корень:** `manifest.webmanifest`, `service-worker.js`, `offline.html` — **0 байт
  (пустые заглушки)**.
- **`client_reference`:** те же файлы **рабочие** (896 / 1275 / 910 байт).

Поскольку база — `client_reference`, PWA берём из него. При изменении списка стилей
обновить `ASSETS` в его `service-worker.js` и поднять версию кэша, иначе отдаётся
старый кэш.

---

## 3. Стратегия слияния (под светлую базу примера)

Так как оболочка берётся из `client_reference` (светлый UI), а логика/карточки — из
корня, конфликты решаем без переписывания JS-классов:

1. **Единый набор CSS-переменных.** Значения — из светлого `client_reference`, имена
   свести к одному набору (7 общих `--var` не должны иметь двух значений).
2. **Cascade Layers.** `@layer base, client, legacy, overrides;` — визуальный слой
   примера (`client`) ведёт; функциональные классы корня (`legacy`) не перекрываются
   по структуре; точечные фиксы — в `overrides`. Без `!important`.
3. **Namespacing спорных классов** корня (например, `.active` в статусах) — узкими
   селекторами в `overrides`, без переименования в разметке.
4. Держать `main.css` с `@import` двух источников — легче откатывать и отлаживать.

---

## 4. Дизайн — светлый (решение заказчика)

Уходим от тёмной темы корня. Базовая палитра — светлая из `client_reference`.
Токенизировать: `--bg`(светлый), `--surface`, `--text`, `--accent`, статусные
`--green/--yellow/--red/--cyan`. Тёмный сайдбар допустим как контраст. Цель — светлая,
воздушная, читаемая система (сотрудникам приятнее работать).

## 5. Команды для точечного диффа (когда понадобится)

```bash
grep -oE '\.[a-zA-Z0-9_-]+' style.css | sort -u > /tmp/root.cls
grep -oE '\.[a-zA-Z0-9_-]+' ART-LINE_OS_v1.6/client_reference/styles.css | sort -u > /tmp/cli.cls
comm -12 /tmp/root.cls /tmp/cli.cls          # общие классы
grep -hoE '\-\-[a-zA-Z0-9_-]+' style.css ART-LINE_OS_v1.6/client_reference/styles.css | sort -u  # переменные
```

## 6. Критерий готовности

Ни один `--var` не имеет двух значений; SPA-навигация по секциям работает; светлая
тема примера; карточки/чат/табы/загрузчик функционируют; мобильный брейкпоинт (≤768px)
сворачивает сайдбар; service-worker отдаёт новый CSS (версия кэша поднята); без
добавленных `!important`.
