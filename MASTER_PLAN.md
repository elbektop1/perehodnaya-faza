## 1. Что у нас есть (проверено по коду)

Три составляющих в репозитории:

- **Корень** (`app.js` 144 КБ, `calculator.html`, `style.css`, `reference_data.js`) —
  твой рабочий прототип. Тёмная тема. Сильная сторона — **живая бизнес-логика**:
  FSM заказов (7 статусов), 9 ролей, калькулятор себестоимости с PIN, справочники.
- **`ART-LINE_OS_v1.6/client_reference`** (`index.html` 224 КБ, `styles.css` 87 КБ,
  `app.js` 58 КБ) — эталон-пример. Светлый, 29 экранов, есть заготовки CRM,
  клиентов, вопросов, импорта, календаря, новостей — на демо-данных.
- **ТЗ заказчика** (.docx) — полное продуктовое видение: длинная цепочка заказа
  (~28 стадий), обязательные бизнес-блокировки, роли, дорожная карта v2.1→v3.0.

Ключевые факты (из `REPO_VALIDATION.md`):
- Реальная FSM корня: `new → design → rework → approval → production → ready → done`.
  «Принять в работу» — флаг `acceptedBy` + guard `requiresAccepted`. Статусы двигают
  4 роли: manager, designer, worker, production_manager.
- Роли в коде (9): director, admin, assistant, manager, designer, economist,
  accountant, worker, production_manager. Маржа гейтится ролями (`economist`/
  `director`), PIN — отдельно в калькуляторе.
- `client_reference` уже содержит рабочие функции: `renderHistory`,
  `renderQuestions`, `renderClientFiles`, `openClientTab`, парсер импорта
  (`splitRows`/`detectDelimiter`), `applyRole`, `navTo`, демо-данные
  (`baseClients`, `historyItems`, `questions`, `sampleCsv`). CRM/клиенты/вопросы/
  импорт — на уровне интерактивного демо, без персистентности.

## 2. Целевая фронтенд-архитектура

Берём **оболочку `client_reference`** (светлый UI, App Shell, сайдбар, секции,
компоненты Hero Card / Timeline / Tabs / календарь) и **вживляем в неё рабочую
логику корня** (FSM заказов, роли, калькулятор). Всё держим в памяти за единым
слоем данных, готовым стать API.

```
┌─────────────────────────────────────────────┐
│  UI Layer  — из client_reference (светлый)    │
│  index.html (секции) + styles.css + компоненты │
├─────────────────────────────────────────────┤
│  Logic Layer                                  │
│   • FSM заказов (TRANSITIONS корня)           │
│   • Роли/меню (расширенный roleVisibility)    │
│   • Калькулятор (calculator.html — не трогать) │
│   • Модули фишек: CRM, calendar, news, tasks, │
│     questions, client-history                 │
├─────────────────────────────────────────────┤
│  Data Layer — store.js (в памяти)             │
│   репозиторий getX()/saveX() → позже fetch()  │
│   сущности: orders, clients, employees,       │
│   tasks, questions, news, events, history     │
└─────────────────────────────────────────────┘
```

**Принцип «данные управляют поведением»** из твоего CLAUDE.md сохраняем: роли, меню,
статусы, справочники — таблицы-объекты, расширение = строка в таблицу.

**Data Layer.** По CLAUDE.md — **без localStorage**. Делаем `store.js`: все данные в
JS-объектах в памяти + функции-репозитории (`getOrders()`, `saveOrder()`,
`getClients()`…). Позже тело функций меняется на `fetch('/api/...')` без правки UI.
> ⚠️ Решение к подтверждению: если заказчику для демо нужна персистентность между
> перезагрузками — временно разрешить localStorage только внутри `store.js`. По
> умолчанию — память (данные сбрасываются на F5, для прототипа приемлемо).

## 3. Роли (целевой набор)

За основу — `roleVisibility` из `client_reference`, расширенный до твоих ролей.
Держим раздельно `economist`, `technologist`, `assistant` (твоё решение).

| Роль | Источник | В целевой системе |
|:--|:--|:--|
| director / leader | корень + пример | Руководитель: всё, пульс, настройки |
| admin | корень | Технический админ (можно объединить с director — открытый вопрос) |
| assistant | корень | Помощник директора: как менеджер минус финансы/калькулятор |
| manager | оба | CRM, клиенты, заказы, расчёты, счета |
| designer | оба | Макеты, бланки, вопросы по макетам |
| technologist | пример/ТЗ | Тех-параметры, формы, произв. пакет (маржу не видит) |
| production_manager | корень | Сборщик форм, очередь, план производства |
| economist | корень | Закупки, себестоимость, предложения |
| accountant | оба | Финансы, счета, оплаты, отсрочки |
| worker / printer | оба | Очередь печати, статус готовности |
| logist | ТЗ (будущее) | Отгрузка — later |

Меню/видимость секций — из таблицы `roleVisibility` (расширить под эти роли).
Маржа/себестоимость — ролевой гейт (`economist`/`director`/`accountant` по ТЗ), плюс
PIN внутри калькулятора. Менеджер себестоимость не видит (прямое требование ТЗ §10.6).

## 4. Приоритетные фишки — статус и работа

Для каждой: что уже есть в `client_reference`, что доделать, критерий готовности.

### 4.1. CRM (главный приоритет)
- **Есть:** секция `crm`, воронка (стадии из ТЗ §10.4), демо-клиенты, напоминания.
- **Доделать:** привязать к `store.clients`; действия «добавить клиента», «итог
  звонка», «след. действие», «создать задачу», «сформировать КП»; подсветка
  просрочек и «клиентов без следующего шага»; связь клиент → заказы.
- **Готово, когда:** менеджер ведёт клиента по воронке, видит просрочки касаний,
  из карточки создаёт заказ/задачу/вопрос.

### 4.2. История взаимодействия с клиентом
- **Есть:** `renderHistory`, вкладка «История» в карточке клиента, `historyItems`.
- **Доделать:** единый лог событий `store.history` (звонки, письма, смена статуса,
  задачи, вопросы) с автозаписью из всех модулей; фильтр по типу.
- **Готово, когда:** на карточке клиента виден хронологический таймлайн всех касаний.

### 4.3. Календарь каждого сотрудника
- **Есть:** секция `calendar` (сетка событий).
- **Доделать:** события с полем `assigneeId`; фильтр «мой календарь»; типы событий
  (звонок, задача, дедлайн заказа, отгрузка, оплата); связь с задачами/заказами.
- **Готово, когда:** сотрудник видит свои события, руководитель — общие.

### 4.4. Новостная лента компании
- **Есть:** секция `news`, кнопка «Ознакомлен».
- **Доделать:** `store.news`; публикация руководителем (всем/отделу); отметка
  «Ознакомлен ✓» по сотруднику; руководитель видит, кто прочитал.
- **Готово, когда:** руководитель публикует новость, сотрудники отмечают прочтение,
  видна статистика ознакомления.

### 4.5. Задачи от руководителя
- **Есть:** секция `tasks`.
- **Доделать:** `store.tasks` (номер `ЗАД-XXXX`, поля из ТЗ §10.16); руководитель
  назначает исполнителя и роль; статусы; связь с клиентом/заказом; «мои задачи».
- **Готово, когда:** руководитель ставит задачу сотруднику, тот видит её у себя и
  меняет статус; просрочки подсвечены.

### 4.6. Вопросы между участниками (на любом этапе)
- **Есть:** `renderQuestions`, секция `questions`, демо `questions` (`ВОП-XXXX`).
- **Доделать:** `store.questions` (поля ТЗ §10.17: тема, автор, адресат, срочность,
  этап, связь с заказом/клиентом, статус); задать вопрос из карточки заказа/задачи
  любому участнику; открытый вопрос влияет на «риск» заказа.
- **Готово, когда:** участник любого этапа задаёт вопрос другому участнику с
  привязкой к заказу; адресат видит его у себя; вопрос закрывается ответом.

## 7. Обязательные бизнес-блокировки (из ТЗ §13 — закладываем как guards)

Их нет в текущей FSM, но целевая система обязана их иметь (часть — уже в Milestone 1
как проверки перед статусом, часть — после оплаты вместе с финансами/документами):

1. Нельзя в печать без подписанного бланка. *(готовим точку расширения в FSM)*
2. Нельзя отгрузить без оплаты или согласованной отсрочки. *(после оплаты — финансы)*
3. Нельзя менять подписанный документ без новой версии. *(после оплаты — документы)*
4. Нельзя менять условия отсрочки без повторного согласования. *(после оплаты)*
5. Нельзя терять историю действий; нельзя скрыть смену цены/срока/статуса/ответственного.
   *(журнал действий закладываем сразу в `store.history`)*

Guard'ы делаем **чистыми функциями** (без DOM) — переедут на бэкенд без переписывания.

   `FSM_ANALYSIS.md`, `ROLE_PERMISSION_MATRIX.md`, `ENTITY_MODEL.md`,
   `CSS_MIGRATION_ANALYSIS.md` — их надо привести к подтверждённым фактам (раздел 7
   REPO_VALIDATION) перед использованием.
